# Audio ABI checkpoint

Date: 2026-08-26

This checkpoint separates verified Tetris resource loading and gameplay-side
audio events from unverified physical output. The desktop sink can decode
supported files when a headed host has an output device, but headless runs do
not prove timing, overlap, or mixer parity.

## Regression gate

The earlier no-input corpus smoke reached the normal watchdog exit for all 20
bundles after the resource-indexed audio-event change. The report and per-title
logs are:

```text
/tmp/fliwheel_regression_20260826_audio_events/20260825_233454_decrypted_games.md
/tmp/fliwheel_regression_20260826_audio_events/20260825_233454_logs/
```

No panic, fatal exception, unmapped access, or memory-fault signature appeared
in that sweep. The newer interactive matrix found a reproducible Hold'em fault
under scripted input; see
`docs/game_tests/20260826_interactive_matrix.md`. Neither sweep is a full
gameplay or sound test.

## Measured resource path

With `CLICKY_AUDIO_TRACE=1`, Tetris resolves its guest filename pointers back
to the bundle assets. The pointer is one byte before the C string in this
callsite, so the tracer recognizes the offset and logs the host path. The
focused frame-correlated artifact is:

```text
/tmp/fliwheel_tetris_gameplay_audio_trace_20260826_b.log
```

The parsed startup path registers these real assets:

```text
Drop.wav Move.wav MoveFail.wav Hold.wav Clear.wav Tetris.wav
Level.wav GameOver.wav Lock.wav Menu.wav
```

The observed Tetris ordinals are:

```text
0, 1, 7, 8, 9, 10, 11, 12, 17, 18, 23, 40, 43, 48, 51, 52, 53, 55, 56
```

The current `AsyncFileIO` path stages WAV headers and offset-based payload
reads. The WAV bytes do not arrive as direct `Audio` arguments; the remaining
binding is through the runtime's audio buffer/source objects.

## Gameplay reachability

The input-scripted Tetris run now reaches the board and produces repeated
gameplay-side calls. In the focused trace, the left, right, and down events
are visible at frames 300, 330, and 400; each is followed by:

```text
Audio:13, Audio:14, Audio:15, Audio:2
```

Those calls use `r0=0xffffffff`, `r1/r2=0x7800`, and the shared table pointer
`r3=0x18025ec8`. They do not carry a direct WAV pointer or a resolved sound
slot. Startup separately registers all ten WAV resources through `Audio:0`
and allocates/configures the shared audio state, but the resource-to-buffer
handle relationship is still unresolved.

The gameplay control evidence is recorded in
`docs/game_tests/20260826_tetris_gameplay_controls.md`.

## Resource-indexed event routing

The current HLE preserves the guest resource index after the Tetris startup
`Audio:0` handles are released. The guest consumer at `0x18003eb8` invokes
`Audio:13/14/15/2` as one logical trigger; fliwheel queues one host event for
that quartet and resolves it through the startup WAV catalog. The focused
artifact is:

```text
/tmp/fliwheel_tetris_audio_events_20260826.log
```

The scripted run resolved these triggers without changing the framebuffer
results:

```text
frame 55, 90, 111: type 0 index 9 -> Menu.wav
frame 300, 330:     type 0 index 1 -> Move.wav
frame 400:          type 0 index 0 -> Drop.wav
```

The desktop EAPP frontend now drains this queue into a persistent `rodio`
output stream for WAV/MP3/FLAC/OGG assets. `EAPP_AUDIO_DISABLE=1` disables the
frontend sink for deterministic visual runs. The headless artifact validates
event identity and asset resolution; it does not claim that a physical output
device was available during the headless test.

This observer is intentionally scoped to bundle `66666`. The corpus-wide
interactive probe showed that the same virtual addresses are unrelated code
in other game binaries; treating their registers as Tetris resource IDs
created fabricated events. Other title families need their own measured Audio
ABI before they are routed to the host sink.

## Stream-manager and channel evidence

The return-path probe is:

```text
/tmp/fliwheel_tetris_audio_stream_manager_trace_20260826_b.log
```

It shows the audio-stream manager accepting the sampled WAV requests: the
initiator returns `r0=1` at `0x1801d840`, and the manager returns slot `r6=0`
at `0x1801d858`. The secondary-owner path at `0x1801d824` also reports valid
byte counts and a selected slot. There is no observed `-1` return from this
manager in the sampled startup sequence, so the resource-table `-1` values are
not evidence of a failed WAV read.

The adjacent channel-status watch is:

```text
/tmp/fliwheel_tetris_audio_channel_watch_20260826.log
```

The guest zeroes the channel-status area at `0x1802400c` and sets the type-1
channel active at `0x18005914`. Separately, the resource table at
`0x18025ec8` is populated by the `Audio:0` callsite and later reset to `-1`
by the guest release path after `Audio:1`. Gameplay then reaches
`Audio:13/14/15/2` with those released entries. This identifies the remaining
boundary as the lifetime/meaning of the Audio object handles and their source
buffers, rather than the asynchronous file path.

The pre-handle callsite/lifetime probe is:

```text
/tmp/fliwheel_tetris_audio_resource_register_20260826.log
```

It captures all ten registrations at guest PC `0x18005498`: type `0`, indices
`0..9`, active status byte `0x01`, and pre-call table entries `-1`. The import
trace's `Audio:0 r0=1` is therefore the active channel/count argument loaded by
the guest, not the table type. This is the baseline captured before the HLE
returned synthetic identities: every `Audio:0` returned `0`; the corresponding
WAV was read successfully, then the guest called `Audio:23` and `Audio:1` with
that handle and cleared the global slot back to `-1`.

The stateful follow-up is:

```text
/tmp/fliwheel_tetris_audio_resource_handles_20260826.log
```

The HLE now allocates identities `1..10` for the ten registrations and tracks
them through release. The first guest `Audio:23` for each identity is observed
as known, while the later duplicate teardown calls are explicitly observed as
already released. This models allocation/release identity without claiming
that the identity has yet been bound to a playable PCM source. The guest still
clears the shared table entries before gameplay, so the consumer-side `-1`
values remain an open reverse-engineering target.

## Open boundary

Tetris now provides a verified gameplay-side transition and an
evidence-backed host event path. The WAV files are decoded by the desktop sink
when a device is available. The remaining accuracy boundary is overlap/mixing
semantics and the source-buffer ABI for titles whose consumer index cannot yet
be resolved from startup resource reads.

The next audio gate is to correlate the now-stable source identity with the
`Audio:13/14/15/2` consumer and separately model the `Audio:40` buffer and
`Audio:56` queue calls for non-Tetris variants, then add a captured waveform
regression for the desktop sink.

The local firmware images were inspected as supporting material, but their
packed `Firmware.MSE` strings alone do not establish this game-framework ABI;
they are not used as a substitute for a measured guest call trace.
